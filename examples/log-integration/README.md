# MongoDB::Atlas::LogIntegration examples

These examples configure `S3_LOG_EXPORT` through the current Atlas `/logIntegrations` API. They do not configure the deprecated `/pushBasedLogExport` feature. See [Export Logs to AWS S3 Buckets](https://www.mongodb.com/docs/atlas/export-logs-external-sinks/) for prerequisites and supported logs.

Activate or privately register `MongoDB::Atlas::LogIntegration` in the stack's AWS account and Region, with an execution role such as [execution-role.yaml](../execution-role.yaml), and configure an [Atlas credential profile](../../README.md#mongodb-atlas-api-keys-credential-management). The combined example also needs `MongoDB::Atlas::CloudProviderAccessSetup` and `MongoDB::Atlas::CloudProviderAccessAuthorization`.

## Create the role and authorization with the integration

[log-integration-with-cloud-provider-access.yaml](./log-integration-with-cloud-provider-access.yaml) registers a new Atlas role, creates an AWS IAM role with its trust policy and S3 permissions, authorizes it, and creates the log integration. It uses an existing S3 bucket in the same AWS account as the stack. Use a bucket with SSE-S3 default encryption for this example, and an eligible Atlas cluster (`M10+`, MongoDB 7.0 or later) to produce logs.

| Parameter | Value |
| --- | --- |
| `ProjectId` | Atlas project ID. |
| `BucketName` | Existing S3 bucket name, not its ARN. |
| `Profile` | Atlas credential profile; defaults to `default`. |
| `PrefixPath` | Log destination prefix; defaults to `mongodb/logs`. |
| `LogType` | One log type; defaults to `MONGOD`. Audit log types require auditing to be enabled on the source clusters. |

The template gives the IAM role a 12-hour maximum session duration. Its inline policy allows `s3:ListBucket` and `s3:GetBucketLocation` on the supplied bucket, and `s3:GetObject` and `s3:PutObject` on its objects. The bucket policy and any organization policies must also permit that access. The bucket remains under your management, including its retention settings and exported objects.

After setting the variables below to your values, deploy from this directory:

```bash
aws cloudformation deploy \
  --template-file log-integration-with-cloud-provider-access.yaml \
  --stack-name atlas-s3-log-integration \
  --region "$AWS_REGION" \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides \
    ProjectId="$ATLAS_PROJECT_ID" \
    Profile="$ATLAS_PROFILE" \
    BucketName="$LOG_BUCKET_NAME"
```

`CAPABILITY_IAM` acknowledges creation of the IAM role. Its name is generated by CloudFormation.

`IamRoleId` takes `CloudProviderAccessSetup.RoleId`, the 24-character **Atlas registration ID**, rather than an AWS ARN or AWS IAM role ID. `DependsOn: CloudProviderAccessAuthorization` makes the log integration wait for authorization. The references alone would only make it wait for setup. The inline permissions are part of the IAM role, so they are created before authorization and remain until the integration has been removed.

Deleting this stack removes the log integration before authorization and IAM role cleanup. The current authorization resource deletes the whole Atlas registration. The existing S3 bucket and previously exported logs remain. See the [Cloud Provider Access guide](../cloud-provider-access-authorization/README.md) for deletion, shared-role, and rollback behavior.

For SSE-KMS, extend the role's permissions for the KMS key and ensure the key policy permits access before using that bucket. Setting `KmsKey` on a log integration does not grant KMS permissions. This additional configuration is outside the combined example.

## Use an already authorized role

[log-integration.json](./log-integration.json) creates only the integration. Supply `ProjectId`, `BucketName`, and the already authorized Atlas `IamRoleId`. The IAM role must already trust Atlas and have the bucket permissions. `Profile` defaults to `default`, `PrefixPath` to `mongodb/logs`, and `LogType1` to `MONGOD_AUDIT`; select a log type produced by your clusters. `LogType2` and `KmsKey` are optional.

If moving from legacy push-based log export, follow the [Atlas migration procedure](https://www.mongodb.com/docs/atlas/push-logs/#migrate-to-external-log-sinks): validate the new integration before disabling the old export. This CloudFormation resource does not expose the API's `useLegacyPathStructure` option, so review destination paths and downstream log processing when migrating.
